# Пошаговая автоматизация с использованием Bash, Docker и Ansible
## Запуск и тестирование
### 1. Запуск скрипта:

1. Клонировать репозиторий
```git clone https://github.com/Nuikut/HTTPStatusCodes && cd HTTPStatusCodes```

2. Выдать необходимые права
```cd Script && chmod +x httpcodes.sh```

3. Запустить скрипт
```./httpcodes.sh```

### 2. Запуск контейнера

``` 
docker run --rm \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --read-only \
  --pids-limit 4 \
  --memory 8m \
  --memory-swap 8m \
  --cpus 0.5 \
  nuikut/http-status-check:latest
```

### 3. Запуск ansible playbook

1. Клонировать репозиторий
```git clone https://github.com/Nuikut/HTTPStatusCodes && cd HTTPStatusCodes```

2. Отредактировать inventory
```cd Ansible && vi inventory.ini```

3. Установить зависимости
```ansible-galaxy collection install -r collections/requirements.yml```

4. Запустить playbook
```ansible-playbook -i inventory.ini playbook.yml```

## Обзор
### 1. Работа со скриптом
Для выполнения первого этапа был написан скрипт на Bash, обращающийся к сервису https://httpstat.us и обрабатывающий ответы в соответствии с указанным в задании алгоритмом. Сервис по всей видимости переехал и URL напрямую не открывается, поэтому использовалось зеркало https://tools-httpstatus.pickup-services.com. 

Скрипт выполняет 5 запросов; запрашиваемые ресурсы (статус-коды) выбираются случайно из всего списка разрешённых общепринятых статус кодов, указанного на сервисе.

**Важное замечание:** задание не описывает поведение при обработке исключения, поэтому принято три решения:
1) Обработкой исключительной ситуации считается вывод в консоль сообщения с пометкой ERROR вместо INFO
2) Исключительная ситуация не прерывает исполнение скрипта и не приводит к завершению с status code 1. Это спорный момент, т. к. с одной стороны исключительная ситуация не всегда должна приводить к аварийному завершению, однако в практической задаче, например CI, такой скрипт должен завершаться с 1, иначе джоба не упадёт и логи никогда не будут прочитаны 

В итоге оставлено так для удобства работы с ansible и с допущением, что это лишь модель реального скрипта

3) Скрипт не прерывает своё исполнение, но завершается с exit code 1 при системных ошибках, связанных с получением HTTP ответа: если нарушена сетевая связность, не запускается curl и т. д. Тогда лог помечается CRITICAL и в конце скрипт завершается с 1.

### 2. Работа с Docker
Для выполнения этого этапа был написан простой Dockerfile. Можно было бы объединить оба RUN в один и chmod исполнить при COPY, но для читаемости было решено оставить так. 

Для безопасности скрипт исполняется от пользователя appuser, а также применяются правила безопасности при запуске контейнера: cap_drop; security_opts; read_only fs; минимально возможное ограничение по PID, обеспечивающее работу приложения; а также ограничения по памяти и cpu.

### 3. Автоматизация процесса с помощью Ansible
Для автоматизации были написаны ansible роли и playbook, запускающих их. Роль docker-install поддерживает debian и redhat дистрибутивы и осуществляет установку в соответствии с официальной документацией docker. 
Для проверки работоспособности был создан дополнительный репозиторий, в котором автоматически проводились тесты. Финальный результат можно просмотреть по [ссылке](https://gitlab.mouse82kg.space/Nuikut/ansible-testing/-/jobs/505).

Vars и defaults определены с учётом необходимости дальнейшей кастомизации: имена контейнеров, путь к Dockerfile, контекст сборки и имя образа вынесены в легко переопределяемые параметры, а URL репозиториев для установки Docker заданы на более высоком уровне переменных Ansible, т.к. они являются общими для окружения и не предполагают частого изменения
